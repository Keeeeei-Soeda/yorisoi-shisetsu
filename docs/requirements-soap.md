## 1. 目的

訪問薬剤師（在宅・施設対応）が、訪問先で取った箇条書きメモを入力するだけで、AI が SOAP 形式（Subjective / Objective / Assessment / Plan）に自動整形してくれる機能を、`yorisoi-shisetsu`（フォーク先）プロトタイプに追加実装する。

## 2. 背景と戦略的位置づけ

### 既存の yorisoi-shisetsu の状態

- 訪問ラウンド管理 + 録音ベースの患者ブロック分割UI が実装済み
- SOAP表示・コピー機能（`buildSoapText`/`buildHomeVisitText`）、`ClinicalData` 型は実装済み
- **しかし AI 生成機能は未実装**（SOAP データは `data/rounds.ts` のハードコーディング）
- READMEに `GEMINI_API_KEY` 必要と書いてあるが、現状はモックデータ表示のみ

### 本機能の戦略的位置づけ

このリポにとって **「最初の実働 AI 機能」** となる。

- 録音ベースの完全自動化（長期的ゴール）はまだ技術的・運用的ハードルが高い
- まずは **「箇条書き入力 → SOAP整形」** という最もシンプルな AI 補助機能から始める
- ユーザー（訪問薬剤師）の現実の業務フローに直結する：
  1. 訪問中に箇条書きでメモ取り（紙・iPad）
  2. 帰社後 or 移動中に本機能で SOAP 整形
  3. 既存の SOAP表示・コピー機能で薬歴ソフトへ転記
- 録音→自動分割という既存機能の上位互換ではなく、**並列・補完する別フロー**として配置

### ビジネス上の狙い

- 訪問薬剤師は店舗薬剤師より痛みが深い：紙メモ → 事務所清書という非効率が日常
- 競合（カケハシMusubi等）は店舗薬剤特化、訪問特化はまだ薄い → ブルーオーシャン
- このプロトタイプを β顧客（訪問対応薬局・薬局チェーンの訪問部門）にデモする素材として活用

## 3. 位置づけ（プロダクトフェーズ）

**プロトタイプフェーズ**。
顧客に見せて反応を取ることが第一目的。本番運用（マルチテナント・電子薬歴連携など）は別プロジェクトで構築する。

## 4. ターゲットユーザー

- **メインユーザー**: 訪問薬剤師（在宅医療・施設訪問担当）
- **副次ユーザー**: 訪問対応薬局の管理薬剤師
- **利用シーン**:
  - 訪問終了後、車内・休憩中・帰社後にメモを SOAP 整形
  - 録音が取れなかった訪問のフォローアップ
  - 録音ベース機能との併用（録音は高度な訪問、簡易メモは定型訪問）

## 5. ユーザーストーリー

```
訪問薬剤師として、
訪問中に取った箇条書きメモ（iPadや紙）を入力するだけで、
SOAP 形式に整理された薬歴ドラフトを得たい。
なぜなら、事務所戻ってからの清書時間（1患者あたり10-15分）を
1-2分に短縮したいから。
```

## 6. 機能要件（MVP）

| ID | 機能 | 優先度 | 受け入れ基準 |
|---|---|---|---|
| F-01 | クイック入力画面への遷移 | Must | サイドバー上部タブ「メモから作成」から遷移可 |
| F-02 | 患者選択 | Must | 既存施設名簿（roster）または「新規・未登録」から選択 |
| F-03 | 訪問先・日付の指定 | Must | 既存FACILITIES から選択、日付はデフォルト今日 |
| F-04 | 箇条書きメモ入力 | Must | textarea で自由入力、プレースホルダで例示 |
| F-05 | SOAP 自動生成 | Must | Gemini API 呼び出し、30秒以内に4セクション出力 |
| F-06 | SOAP 編集 | Must | 4セクションそれぞれ独立して編集可能 |
| F-07 | 保存・履歴閲覧 | Must | localStorage に保存、「履歴」タブから閲覧 |
| F-08 | クイックSOAP専用フォーマットでのコピー | Must | `lib/formatters.ts` の `buildQuickSoapText` を使用 |
| F-09 | 再生成 | Should | 同じ入力で AI 再生成 |
| F-10 | 薬学的フォーカス情報の補完 | Could | medications・red_flags も AI 抽出（既存型を埋める） |

## 7. 非機能要件

- **パフォーマンス**: SOAP 生成は 30 秒以内
- **永続化**: localStorage（プロトタイプにつきブラウザ依存でOK）
- **API**: Gemini API キー（`.env.local` に新規設定）
- **structured output**: JSON 形式で {S, O, A, P} を取得、既存 `ClinicalData.soap` 型に合わせる
- **エラーハンドリング**: API エラー時はユーザーにわかりやすく通知
- **スタイル**: 既存 Tailwind パターン（teal系アクセント、slate系ベース）に合わせる

## 9. SOAP 形式の定義（プロンプト設計用）

訪問薬剤師業務に特化した解釈：

- **S (Subjective)**: 患者の自覚症状・訴え・服薬遵守状況・生活背景・家族からの情報など主観的情報
- **O (Objective)**: バイタル・他覚的所見・お薬手帳記載内容・残薬状況・服薬カレンダー確認結果など客観的情報
- **A (Assessment)**: 薬剤師としての評価・薬学的問題点の特定・前回からの変化
- **P (Plan)**: 薬学的介入計画・服薬指導内容・次回訪問時の確認事項・他職種への申し送り（医師・看護師・ケアマネ）

判断に迷う情報があれば、訪問薬剤管理指導の現場で薬剤師が最も使いやすいセクションに配置するよう指示する。

## 10. Few-shot 例（プロンプトに含める）

訪問特化の3例：

### 例1: 施設入居者の継続フォロー
入力：
- 80代女性、特養入居
- 降圧剤の血圧コントロール良好（朝120/70台）
- 認知症進行で残薬多め、服薬支援強化が必要
- 食事量低下、便秘の訴え増えてる
- 看護師と次回までに排便コントロール相談予定

期待出力：S/O/A/Pにきれいに分解

### 例2: 在宅患者の初回訪問
入力：
- 75歳男性、心不全で退院後初回訪問
- 妻が服薬管理担当、独居時間あり
- お薬カレンダーまだ未導入
- 利尿剤のタイミングで失禁懸念
- 妻も高齢で服薬管理に不安あり
- ケアマネに次回MTGで相談したい旨報告

### 例3: 認知症患者の服薬コンプライアンス
入力：
- 85歳女性、グループホーム入居
- 認知症中等度、服薬拒否の日あり
- 抗認知症薬の貼付剤に変更検討中
- 食欲低下、体重減少傾向
- 主治医に剤型変更提案する方針
- 介護スタッフへの説明資料も準備必要

## 11. 既存資産との関係

| 既存資産 | 本機能での扱い |
|---|---|
| `FACILITIES` / `ROUNDS` (data/rounds.ts) | 施設・日付選択で参照（読み取りのみ） |
| `ClinicalData` 型 (types.ts) | SOAP 生成結果の格納先として使用（既存型変更しない） |
| `buildSoapText` / `buildHomeVisitText` | **触らない**。クイックSOAP用は新規 `buildQuickSoapText` を作成 |
| `SectionHeader` (components/) | 新規画面でも使用 |
| Tailwind クラスパターン（teal/slate系） | 新規UIでも統一 |
| 既存の Toast コンポーネント | 保存通知・エラー通知に流用 |
| `components/SoapView.tsx`, `PatientSidebar.tsx` | **無視**（AI Studio 時代の残骸、未使用） |

## 12. 成功指標

プロトタイプとしての成功基準：

- [ ] 渓さん自身が訪問薬剤師目線で試して「これ使える」と思える品質

- [ ] SOAP 生成の精度が、薬剤師目線で「修正10%以下」レベル
- [ ] 既存のラウンド機能と違和感なく共存している（UIの一体感）
