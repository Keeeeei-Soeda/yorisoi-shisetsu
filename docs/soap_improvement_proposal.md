# yorisoi-shisetsu SOAP整形機能 改善提案書

評価対象: 特養入居者ケース（例1）の AI 生成結果  
現状スコア: **8.5 / 10**  
目標スコア: **9.5 / 10**

---

## エグゼクティブサマリ

現状の AI 出力は、SOAP の論理構造（特に A → P の連鎖）が正しく組まれており、実用レベルに到達している。一方で **施設薬歴特有の文脈（発言主体・多職種連携）** と **算定要件（薬剤名解像度）** の2軸で改善余地が大きい。

本提案では4つの改善提案を提示し、Few-shot とシステムプロンプトへの追加ルールで実装可能とする。validator レイヤの追加も併せて推奨する。

## 提案 1: 発言主体タグの導入

### 課題
施設薬歴では、情報源が **本人 / 家族 / 介護スタッフ / 看護師** のいずれであるかで臨床的意味が大きく変わる。特に認知症患者では本人の主訴が取れず、スタッフからの代理情報が中心になるが、現状の出力ではこれが S に混在して書かれている。

### As-Is

```
S: - 便秘増悪・食事量低下を訴え
```

**問題点:**
- 「誰が」訴えたのかが不明
- 「本人の訴え＝直接的訴え」と「スタッフの観察＝代理的訴え」の臨床的重みが区別できない
- 次回担当者が情報の信頼度を判断できない

### To-Be

```
S:
- [スタッフ] 便秘増悪、食事量低下あり（3日前より）
- [本人] 訴え聴取困難（認知症進行のため）
```

**改善点:**
- 発言主体を `[ ]` でタグ化
- 本人の訴えが取れない場合も、それを明示的に S に書く（情報の「無さ」も情報）
- 時系列情報（3日前より）も可能な範囲で含める

### 実装方法

**Few-shot追加例:**
```
入力: 「介護スタッフより、ここ3日便が出ていないとの報告。本人は意思疎通困難」
↓
S:
- [スタッフ] 排便3日なし
- [本人] 訴え聴取困難（認知症進行）
```

**システムプロンプト追加ルール:**
```
S（主観的情報）の記述ルール:
1. 発言主体を必ず冒頭に [本人] [家族] [スタッフ] [看護師] のいずれかで明示する
2. 本人から情報が取れない場合は [本人] 訴え聴取困難（理由）と明記する
3. 主体が複数の場合は項目を分ける
```

## 提案 2: 薬剤名・用量の必須化

### 課題
現状の O に「降圧剤継続中」とだけ書かれており、薬剤名・用量・用法が抜けている。これは服薬管理指導料の算定要件上、**記載不備に該当するリスク**がある。また次回担当者が薬歴単体で投薬判断できない。

### As-Is

```
O:
- 80代女性、特養入居
- 降圧剤継続中、朝の血圧 120/70台で安定
- 残薬量が通常より多く認められる
- 認知症進行の経過あり
```

**問題点:**
- 薬剤名・用量・用法が記載されていない
- 残薬量が定量化されていない（「多く」では算定不可）
- 血圧の測定主体（誰が測ったか）が不明

### To-Be

```
O:
- 80代女性、特養入居、要介護4
- 処方: アムロジピン5mg 1日1回 朝食後（継続）
- 施設看護師測定: 朝の血圧 120/70台で安定（過去1週間平均）
- 残薬: 約14日分蓄積（通常2-3日分以内）
- 既往: 認知症（HDS-R低下傾向、進行期）
```

**改善点:**
- 薬剤名・用量・用法を完全記載
- 残薬を数値化（「14日分」）
- 測定主体を明示
- 認知症の進行度も客観的指標で記載できれば望ましい

### 実装方法

**システムプロンプト追加ルール:**
```
O（客観的情報）の記述ルール:
1. 薬剤情報は必ず「薬剤名 + 用量 + 用法」のフォーマットで記載する
2. 数値情報は可能な限り定量化する（「多い」→「14日分」）
3. 測定値は測定主体を明示する（薬剤師/施設看護師/家族 等）
4. 服薬中の処方が複数ある場合は全て列挙する
```

**validator 擬似コード:**
```typescript
function validateObjective(o: string, prescription: Prescription[]): ValidationResult {
  const issues: string[] = [];
  
  // 処方薬が記載されているかチェック
  for (const drug of prescription) {
    if (!o.includes(drug.name)) {
      issues.push(`薬剤名「${drug.name}」がOに記載されていません`);
    }
  }
  
  // 「多い」「少ない」「あり」など曖昧表現の検出
  const vagueTerms = ['多く', '少なく', 'やや', 'かなり'];
  for (const term of vagueTerms) {
    if (o.includes(term) && !hasNumericContext(o, term)) {
      issues.push(`曖昧表現「${term}」を定量化することを推奨`);
    }
  }
  
  return { passed: issues.length === 0, issues };
}
```

## 提案 3: Ep/Cp 判定ロジックの明文化

### 課題
現状の P では Ep/Cp の使い分けが曖昧。特に「介護スタッフへ服薬見守りを共有」は、現状では Ep に分類されているが、薬情メモの定義に従えば Cp が適切。判定基準がプロンプトに明示されていないため、出力が不安定。

### As-Is

```
P:
- Ep: 介護スタッフへ服薬見守り・拒否時対応を共有
- Cp: 残薬回収、次回処方調整を医師に情報提供
- Op: 看護師と排便コントロール協議（次回訪問までに）
- Op: 次回確認＝残薬・血圧・排便・食欲
```

**問題点:**
- 「介護スタッフへの共有」が Ep か Cp かが曖昧
- 患者本人への指導（本来の Ep の対象）が無い
- 判定ロジックが暗黙的

### To-Be

```
P:
- Cp: 介護スタッフへ服薬見守り・拒否時対応を依頼（連携アクション）
- Cp: 残薬回収（実行済み）、医師へ処方調整を情報提供
- Op: 看護師と排便コントロール協議（次回訪問までに）
- Op: 次回確認項目＝残薬・血圧・排便・食欲
- Op: 本人への指導は意思疎通困難のため見送り
```

**改善点:**
- Ep/Cp の判定が明確
- 「本人への指導見送り」を Op に明示することで、薬剤師が判断したことを記録
- アクションの実行状況（「実行済み」「依頼」「提案」）を区別

### 実装方法

**Ep/Cp/Op 判定フローチャート:**

```
アクション内容を分析
  ↓
誰に対するアクションか？
  ├─ 患者本人または家族
  │    └─ 情報提供・指導内容 → Ep
  │
  ├─ 医療機関（医師・看護師）
  │    ├─ 疑義照会・処方変更提案 → Cp
  │    └─ 情報共有（提案なし） → Cp
  │
  ├─ 介護スタッフ・他職種
  │    ├─ 依頼・連携アクション → Cp
  │    └─ 情報共有のみ → Cp
  │
  └─ 次回担当薬剤師への申し送り
       └─ 観察・確認事項 → Op
```

**システムプロンプト追加ルール:**
```
P（計画）の Ep/Cp/Op 判定ルール:
- Ep = 患者本人または家族に対する情報提供・指導（教えたこと）
- Cp = 患者本人以外（医師・看護師・介護スタッフ）へのアクション（してあげたこと）
- Op = 次回担当薬剤師への申し送り・観察事項（次の薬剤師にしてほしいこと）

判定の優先順位:
1. アクションの対象者を特定する
2. 患者本人/家族 → Ep、それ以外の人間 → Cp、未来の薬剤師 → Op
3. 本人への指導が困難な場合、その理由を Op に記録する
```

## 提案 4: 算定要件カバレッジ validator

### 課題
服薬管理指導料の必須項目（服用状況・残薬・体調変化・併用薬・既往歴・他科受診・副作用・体質アレルギー・飲食物・後発品の意向・手帳の有無・服薬指導の要点）の記載漏れがあると算定リスク。現状は AI に頼っており、検証層が無い。

### As-Is

AI が出力したものを薬剤師がそのまま受け入れる（または手動で漏れチェック）。

### To-Be

AI 出力後に validator レイヤを通し、必須項目の充足率を判定する。不足項目はフラグを立てて薬剤師に再確認を促す。

### 実装方法

**validator 設計:**

```typescript
interface RequiredItem {
  key: string;
  label: string;
  soapField: 'S' | 'O' | 'A' | 'P';
  keywords: string[];  // 該当検出キーワード
  required: 'always' | 'first_visit_only' | 'when_relevant';
}

const REQUIRED_ITEMS: RequiredItem[] = [
  { key: 'medication_adherence', label: '服用状況', soapField: 'S', 
    keywords: ['服用', 'コンプライアンス', '飲み忘れ', '内服'], required: 'always' },
  { key: 'remaining_drugs', label: '残薬確認', soapField: 'S', 
    keywords: ['残薬', '残り'], required: 'always' },
  { key: 'condition_change', label: '体調変化', soapField: 'S', 
    keywords: ['体調', '症状', '変化', '訴え'], required: 'always' },
  { key: 'concomitant_drugs', label: '併用薬', soapField: 'O', 
    keywords: ['併用', '他院', 'OTC'], required: 'when_relevant' },
  { key: 'medical_history', label: '既往歴', soapField: 'O', 
    keywords: ['既往', '疾患', '病歴'], required: 'first_visit_only' },
  { key: 'side_effects', label: '副作用', soapField: 'S/O', 
    keywords: ['副作用', '有害事象', 'SE'], required: 'always' },
  { key: 'allergy', label: '体質・アレルギー', soapField: 'O', 
    keywords: ['アレルギー', '体質', '過敏'], required: 'first_visit_only' },
  { key: 'guidance_content', label: '服薬指導の要点', soapField: 'P', 
    keywords: ['指導', '説明', '情報提供'], required: 'always' },
  // ... 他の必須項目
];

function validateCoverage(soap: SOAP, patientType: 'first' | 'repeat'): CoverageReport {
  const missing: RequiredItem[] = [];
  const warnings: string[] = [];
  
  const allText = `${soap.S} ${soap.O} ${soap.A} ${soap.P}`;
  
  for (const item of REQUIRED_ITEMS) {
    if (item.required === 'first_visit_only' && patientType !== 'first') continue;
    
    const found = item.keywords.some(kw => allText.includes(kw));
    if (!found && item.required === 'always') {
      missing.push(item);
    }
  }
  
  return {
    coverageRate: 1 - (missing.length / REQUIRED_ITEMS.length),
    missingItems: missing,
    warnings: warnings,
    canSubmit: missing.length === 0
  };
}
```

**UI フィードバック例:**
```
✓ 服用状況: 記載あり
✓ 残薬確認: 記載あり（O: 14日分蓄積）
✗ 副作用: 記載なし — 確認が必要です
✓ 服薬指導の要点: 記載あり

カバレッジ: 87% (7/8)
算定可能: ✗ 副作用項目の追加を推奨
```

## まとめ

現状の AI 出力は **A → P の論理性** という、最も難しくバラつきやすい部分が正しく動いている。これは岡村祐聡氏の指摘する「多くの薬剤師が一番悩む A」の品質を、AI 側でクリアできている証拠。

残された課題は、主に **施設薬歴特有のコンテキスト（発言主体・多職種連携）** と **算定要件レベルの形式整備** で、これらはプロンプト改訂と validator 追加で機械的に解決可能。

Phase 1 だけでも 9.2 まで上がり、Phase 2 完了で 9.5 到達。Phase 3 で算定リスクの体系的排除まで達成できる。
